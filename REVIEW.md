# REVIEW.md

Line numbers refer to the **starter** `app/main.py` from the candidate kit. Shift 09:30-18:30 unless stated otherwise.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `MongoClient(...)`, l.22 | The client returns **naive** datetimes. Any later `.timestamp()` / arithmetic treats them as the server's local time. | On a machine set to IST, a stored `03:58Z` punch converts to an epoch value 5h30m off; comparing a naive value with an aware IST value raises `TypeError` (500). | `MongoClient(..., tz_aware=True, tzinfo=UTC)`: every datetime read back is aware UTC. |
| 2 | `compute_late_minutes`, l.35 | The shift start is built with `punch_in.replace(hour, minute)`, which uses the punch's own zone (naive server-local/UTC), not IST. It also uses the punch's calendar day, which is wrong for an overnight shift. | `punched_at` = 09:45 IST (04:15Z) on a UTC server gives a start of `09:30Z`, so late = 0 instead of 15. Overnight 22:00-06:00, punch 01:00 IST: start resolves to the same day's 22:00, so the minutes are negative and late = 0 instead of 180. | The shift start is computed from the **attendance date** (R1) in IST (`shift_window`). |
| 3 | `compute_late_minutes`, l.36-37 | The grace check runs on truncated whole minutes (`minutes > 10`), not "strictly more than 10:00". | 09:40:30 gives `int(10.5)=10`, so `10 > 10` is false and late = 0. The answer should be 10. R2's own example 09:40:01 also returns 0 instead of 10. | Compare **seconds**: `seconds > 600`, then `seconds // 60`. |
| 4 | `compute_work_hours`, l.41 | `round()` on a binary float is banker's/representation rounding, not half-up (R4). Instants are not truncated to whole seconds first (R1). | 4h29m42s = 4.495 h: `round(4.495, 2)` gives **4.49**, so `half_day` becomes true. The correct answer is 4.50 and `half_day` false. | `Decimal(seconds) / 3600` quantized with `ROUND_HALF_UP`. Instants are truncated with `ms // 1000` at the boundary. |
| 5 | `compute_overtime`, l.44-47 | (a) There is no 30-minute minimum (R3). (b) For an overnight shift the shift end is put on the start date, not the next day. (c) The aware IST end minus a naive `punch_out` raises `TypeError`. | (a) Out at 18:35 gives 5 instead of 0. (b) 22:00-06:00, out 06:40 next day gives 1480 instead of 40. (c) A 500 on every punch-out built from starter-style naive datetimes. | `shift_window()` moves the end to day+1 when `end <= start`. Overtime is `floor` minutes, kept only if `>= 30`. All datetimes are aware. |
| 6 | `EmployeeIn`, `PunchInIn`, l.53-66 | No validation. `emp_code`/email/shift patterns, lengths, `joined_on` as a real date and `shift_start != shift_end` are all unchecked. `status` accepts any string, including `ABSENT`. `punched_at: Optional[int]` in Pydantic's lax mode accepts `"1783312500000"` and `1783312500000.0`, and also accepts seconds (`1783312500`). | `POST /attendance/punch-in {"status":"ABSENT"}` gives 201. `{"punched_at": 1783312500}` gives 201 with a 1970 date. `joined_on: "2026-02-30"` is stored. | Pydantic constraints that mirror the OpenAPI schemas. `EpochMs = StrictInt` with `ge=1e11, le=4102444800000`. `Literal` status enums. A model validator checks that the shift has a length. |
| 7 | `health`, l.73 | Always 200, even when MongoDB is down. The grader uses it as a readiness probe. | Stop Mongo: `/health` still says ok and the next request returns 500. | `ping` the server and return 503 on `PyMongoError`. |
| 8 | `create_employee`, l.79-83 | Check-then-insert with no unique index is a race. | 10 parallel identical POSTs can give several 201s and duplicate `emp_code`s. | A unique index on `emp_code` created at startup. Just `insert_one` and map `DuplicateKeyError` to 409. |
| 9 | `create_employee`, l.82, l.85 | `datetime.now()` is naive local time, so PyMongo stores it as if it were UTC. The response returns a datetime object instead of epoch ms. | On an IST machine `created_at` is stored 5h30m in the future. The response has `"created_at": "2026-..."` (an ISO string), not an integer. | `datetime.now(UTC)`, serialized with `to_ms()`. |
| 10 | `list_employees`, l.93 | `skip = page * page_size`: page 1 skips the first page. | 25 employees, `page=1`: you get rows 21-25 and never see EMP0001. | `(page - 1) * page_size`. |
| 11 | `list_employees`, l.94 | `total` counts the whole collection and ignores the department filter (R10). | `?department=Sales` returns `total` = all employees. | `count_documents(query)` with the same filter. |
| 12 | `list_employees`, l.95 | No sort, so the order is natural/insertion order rather than `emp_code` ascending. Pages are unstable. | Insert EMP0002 before EMP0001: the list starts with EMP0002. | `.sort("emp_code", 1)`, served by the unique index (or `department_emp_code` when filtered). |
| 13 | `list_employees` / `list_attendance`, l.89, l.130 | `page` and `page_size` are unbounded. `page=0` gives a negative skip (a Mongo error, so 500) or odd slicing. `page_size=100000` dumps everything. | `?page=0` returns 500. `?page_size=101` is accepted. | `Query(ge=1)` and `Query(ge=1, le=100)`, so both return 422. |
| 14 | `punch_in`, l.101, l.113 | An unknown employee gives `emp = None`, then `emp["shift_start"]` raises `TypeError`, so 500 instead of 404. | `POST /attendance/punch-in {"emp_code":"EMP9999"}` returns 500. | `get_employee_or_404()`. |
| 15 | `punch_in`, l.102-103 | `datetime.fromtimestamp(ms/1000)` uses the server's local zone and keeps the milliseconds. `date` is the local calendar date, not the IST date (R1), and there is no overnight-shift rule. | On a UTC server a 00:30 IST punch (19:00Z the day before) is filed under the previous day. Overnight 22:00-06:00, a 01:00 punch is filed under the new day. 09:40:00.900 is stored with the .900. | `from_ms()` gives aware UTC truncated to seconds. `attendance_date()` implements R1, including the overnight rule. |
| 16 | `punch_in`, l.104-118 | Check-then-insert with no unique index on (`emp_code`, `date`). | Two simultaneous identical punch-ins both get 201 and two records exist for one day. | A unique index on (`emp_code`, `date`). `insert_one` and map `DuplicateKeyError` to 409. Explained in DECISIONS.md. |
| 17 | `punch_in` / `list_attendance`, l.119, l.149 | Exposes MongoDB's `_id` as `id`. The contract says records have no id and `_id` never appears. Datetimes are returned as datetime objects, not epoch ms. | The response contains `"id": "66a..."` and `"punch_in": "2026-07-06T09:28:00"`. | `serialize_record()` emits exactly the contract fields, converts instants (including those nested in `history[].changes`) to ms, and defaults missing `half_day`/`history`/derived values. |
| 18 | `list_attendance`, l.144-147 | Loads every matching document into Python, sorts and slices in memory. That is O(n) memory and time on 100k records. | `GET /attendance` with no filters reads the whole collection on every request. Explain would show a COLLSCAN. | `find(q).sort(date -1, emp_code 1).skip().limit()` backed by `date_desc_emp_code`, `emp_code_date_unique` and `status_date_desc_emp_code`. `total` is `count_documents(q)`. |
| 19 | `list_attendance`, l.145 | The sort has no tie-breaker on `emp_code`. Records on the same date come back in arbitrary order, so pagination can repeat or skip rows. | Two employees on 2026-07-08: their order changes between calls. | Secondary sort `emp_code` ascending. |
| 20 | `list_attendance`, l.127-129 | `date_from`/`date_to`/`status` are not validated. `date_from > date_to` silently returns nothing, and `status=BOGUS` and `date_from=2026-7-1` are accepted. The string range compare also breaks for non-zero-padded dates. | `?date_from=2026-07-08&date_to=2026-07-01` gives 200 with `[]`. It should be 422. | `IsoDate` validator (strict `YYYY-MM-DD`, a real calendar date), `Status` enum, and an explicit `date_from > date_to` check. All return 422. |
| 21 | module level | No indexes are created at startup, and the seeded DB has only `_id`. Every lookup by `emp_code`/`date` is a collection scan. | `/admin/explain/...` shows COLLSCAN. | `ensure_indexes()` runs in the FastAPI lifespan. `create_index` is idempotent. |

### Looked at and decided are **not** defects
* `load_dotenv()` (l.20): the default is `override=False`, so real environment variables already win over `.env`, as the contract requires.
* `IST = timezone(timedelta(hours=5, minutes=30))` (l.25) is correct. IST has no DST, so a fixed offset is right and no tz database is needed.
* `compute_work_hours`'s formula (`seconds / 3600`) is correct. Only the rounding and truncation are wrong (#4).
* `int(...)` truncation in `compute_overtime` equals `floor` for the positive values that matter. I still use `//` on whole seconds for clarity.
* The `doc.pop("_id")` in `create_employee` is needed because `insert_one` mutates the dict. It is kept implicitly: `serialize_employee` picks the contract fields explicitly.
* Storing `date`, `joined_on` and shift times as strings is intentional (DATA_MODEL.md). Zero-padded `YYYY-MM-DD` strings sort and range-compare correctly, which is why the validators insist on that exact format.
* `if department:` treating `?department=` as "no filter" is arguable rather than wrong. I changed it to `is not None` so an explicit empty value is an exact match, which is consistent with "exact, case-sensitive match".
